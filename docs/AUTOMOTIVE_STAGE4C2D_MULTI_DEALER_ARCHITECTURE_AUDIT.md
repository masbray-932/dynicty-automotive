## 3. Proposed target architecture

Use one application with three separately authorized paths: public requests resolve a verified dealer host; dealer Admin combines that host binding with a current membership; platform operations use an independent platform identity on a fixed platform origin. Keep the single-dealer deployment mode explicit until the cutover. No user-supplied dealer ID, object ID, role claim, or hostname string is itself authority.

1. Resolve trusted request context before querying dealer data. Public context is a read-only dealer/binding/canonical-origin tuple. Dealer Admin context also carries a verified subject, session, membership and permission. Platform authorization separately checks both the named permission and the resolved target dealer.
2. Require context at the server-only repository/DAL boundary. All tenant queries use a trusted owner predicate, including nested relation lookups. Writes use owner and object identifiers in the same mutation or a locked transaction. Avoid global lookup followed by post-query filtering. Return the same not-found result for missing and foreign IDs where appropriate.
3. Enforce relational ownership in PostgreSQL with tenant-qualified foreign keys, not only application checks. Add and verify row-level security (RLS) as defense in depth before a second dealer uses the shared database. Keep explicit query predicates even with RLS. Public reads must also enforce publication state.
4. Separate the bootstrap registry/session/grant lookup path from tenant data access. A least-privileged bootstrap role or narrow lookup interface reads only the identifiers and status needed to construct context. Use distinct runtime privileges for public reads, dealer operations, and restricted platform branding; the normal tenant role does not write branding tables. Migration/backup roles must not serve requests.
5. For RLS, prove the selected Prisma/pool configuration uses the same transaction for transaction-local dealer context and all tenant queries. Missing or invalid context denies reads and writes; apply both visibility and write checks. Runtime roles must not own tables or bypass RLS; verify policy coverage and owner behavior in PostgreSQL. A role that can run arbitrary SQL and change its own context is outside this boundary: parameterize queries and restrict raw SQL/credentials. If the deployed pool or provider cannot enforce this design, block shared-database activation pending a reviewed alternative such as separate databases.
6. Invalidate dealer-specific public output only after commit. Write media cleanup and invalidation events durably with mutations where failure would otherwise leave stale exposure. Record actor, dealer, permission, resource, outcome and correlation ID; never log secrets or session tokens.

## 6. Domain and identity resolution design

**Domain lifecycle and trust**

- Reserve hostnames centrally. For managed subdomains, allocate an allowed label under the configured platform zone, reject reserved labels and collisions, provision DNS/TLS, and verify routing. For custom domains, issue an expiring, single-use ownership challenge tied to the reserved hostname and dealer (e.g. DNS TXT), independently verify ownership and expected edge routing/TLS, and record verification. Pointing DNS at a shared edge alone does not prove assignment. Do not accept user URLs or arbitrary verification callbacks; use a bounded DNS verification job.
- Normalize once at registration and once at request lookup with the same policy: lower-case IDNA ASCII hostname, strip at most one terminal dot consistently, enforce DNS lengths/labels, and reject malformed input, multiple authorities, IP literals, wildcard requests and unexpected ports. Ports for local development must be explicitly configured; build HTTPS origins from verified registry values, never reflected headers. Reserve normalized names transactionally. Public host resolution accepts only exact live bindings.
- Edge TLS and routing must agree with the selected hostname. Reject unknown names at ingress where possible; block direct origin access. Strip incoming `Forwarded`, `X-Forwarded-Host` and internal binding headers, and set a canonical host from the vetted edge route; only the authenticated/private ingress is allowed to pass it. Treat client Host as a public routing selector, not identity. Align Next Server Action origin checks with the same trusted authority; reject cross-origin writes and alias-host writes, including requests from sibling subdomains. Do not reuse IP trust configuration as proof of host trust.
- Resolve the binding and dealer state together. Pending, unknown, archived and suspended hosts return a neutral no-store response with no tenant data, no search indexing and no fallback. Registry errors fail closed. Activation requires verified binding, TLS, one canonical host, valid ownership and the security gates. Suspension blocks session use and reads/writes/media at the authoritative boundary, revokes applicable sessions and purges cached representations. Resume only after explicit approval and verification; revoked sessions do not become valid again.
- Keep legacy mode explicit and mutually exclusive with the registered resolver. While legacy mode is on, allow only an operator-configured exact existing host set and preserve the current `default` row and login flows. In registered mode no failed binding lookup, membership lookup, preview parameter or unknown hostname may call the legacy adapter. The legacy dealer then has an ordinary binding to its new registered ID.

**Identity and sessions**

| Flow | Resolution and invalidation |
|---|---|
| Dealer login | Resolve dealer from canonical verified host before credential/member evaluation. Verify password using existing credential controls; require an active membership and active dealer, with generic failure and rate limits keyed by stable dealer plus the existing abuse controls. Create an opaque session bound to admin, membership, dealer, binding and relevant versions. |
| Dealer request | Verify token hash, expiry and revocation, match dealer/host binding, and check current membership and dealer state server-side before reading or mutating. Use host-only, Secure, HttpOnly cookie with separate platform cookie; do not share a parent Domain. For state changes, verify origin/CSRF as appropriate and recheck membership/dealer under transaction locking or an equivalent atomic fence before commit. An in-flight write either linearizes before revocation or is denied after it; external asset attach must recheck after upload. |
| Membership revocation / suspension | Disable membership or dealer and bump its version in a transaction; revoke matching sessions and purge auth/cache state. Reject the next request even if a cookie remains. Password/account compromise revokes all affected sessions. For domain change, retire the prior binding/version and require fresh login on the new canonical host. |
| Platform admin | Use a separate trusted platform issuer/client and fixed origin. Verify issuer, subject, audience, session and current explicit grants; use MFA for privileged access. A dealer email, cookie or membership grants no platform identity. Restrict platform credentials, privileged operations and audit events to named permissions/targets. Platform access does not imply arbitrary operational impersonation. |
| Public storefront | Resolve a verified binding on the server. No admin cookie or client dealer hint participates. Preview is a separate authenticated no-store path and does not broaden the public read policy. |

## 7. Storage, cache and SEO

| Area | Design |
|---|---|
| Object keys and writes | Use immutable, server-generated `dealers/<dealerId>/<purpose>/<assetId>.<validated-ext>` keys. | Domain change | Publish the new verified canonical binding atomically, invalidate both origins, revoke old-host sessions and update metadata/robots/sitemap. While both bindings are owned and verified, use a reversible public GET/HEAD redirect initially; a permanent redirect is appropriate only after cutover approval. Never redirect Admin mutations or route a retired domain to another owner via old mappings. |

## 8. Migration and rollback strategy

| Stage | Implementation and exit gate |
|---|---|
| 0. | 1. Expand | Add registry/membership/asset tables and nullable owner columns without dropping global constraints or changing existing PKs. Provision one registered ID for the legacy installation and an explicit mapping from Settings `default`. Add supporting indexes and FKs in a reviewed lock-aware order; confirm any online/index/constraint-validation options against the actual PostgreSQL version and migration runner. No registry routing or new dealer writes yet. |
| 2. Backfill | Assign Settings, CMS, existing car/taxonomy and image rows to the verified legacy dealer using bounded, restartable batches. **Rollback boundary.** Before data for a second dealer exists, roll back application behavior only to a reviewed release that still enforces 4C.2B branding protection and is compatible with additive schema and dual-write/freeze state. Reconcile writes and verify host/cache/session state first. Once independent dealer rows or duplicate per-dealer slugs exist, an older global-reader binary or legacy adapter is unsafe. Freeze or suspend traffic, revoke sessions, purge caches and roll forward or revert to a known scoped release. For disaster recovery restore DB and objects to a coordinated point in an isolated environment, reconcile outbox/object manifests, quantify post-backup write loss, reapply revocations/domain holds, rotate credentials as appropriate and verify both tenants before reopening traffic. Do not simply reverse Prisma migrations or assume a database restore restores bucket objects.

## 9. Two-dealer security test matrix

## 10. Implementation sequencing for subsequent stages

1. **Data and identity foundation:** design/review additive DDL, define legacy mapping, implement registry, membership and isolated session primitives; enforce exact dealer domain resolution behind a single-dealer feature gate. Test clean and legacy PostgreSQL fixtures.
2. **Ownership and DAL cutover:** migrate Settings/CMS, taxonomy, inventory and images in dependency order. Replace page and service direct lookups with scoped entry points, prove database constraints and pooled RLS under least privilege. Keep 4C.2B branding write restrictions active.
3. **Media, public routing and operations:** implement provider and asset lifecycle, trusted edge, cache/version and SEO cutover, coordinated restore runbook. Verify old media compatibility without exposing private paths.
4. **Platform and activation:** connect approved platform issuer/grants and separately review any writer; rehearse two dealers in an isolated environment. Cut over the mapped legacy dealer first, then allow a second dealer only after all gates, including rollback, are signed off.

## 11. Open decisions and blockers

| Gate | Needed before enabling registered multi-dealer traffic |
|---|---|
| Platform identity | Name the approved issuer/client, grant owner, MFA and revocation procedure. No web platform writer until verified. |
| Hosting and domain | Confirm managed zone, custom-domain verification operator, TLS/edge support, canonical/alias policy, and ingress-to-origin trust. Unknown-host denial and transfer purge need real staging verification. |
| PostgreSQL and pool | Confirm supported versions and deployment roles, RLS/transaction behavior, constraints, online DDL budget and migration strategy on a restore. No live DB capabilities were inferred from repo files. |
| Private media | R2 writes/deletes are unimplemented in the audited source. Select and verify private provider, visibility, bounded revocation window, backups and cleanup jobs. |
| Data and recovery | Assign accountable owners for legacy mapping, mismatch remediation, migration freeze, DB/object backup and restore, plus monitored cutover. Decide explicit RPO/RTO before activation. |
